# 05 · 联机与服务端设计

> 本文覆盖多人协作的全部链路：Python 房间服务器（`server.py`）的架构与协议、
> 客户端网络层、主机权威同步策略，以及 WebRTC 手动点对点备用通道。
> 面向使用者的部署步骤见根目录 [联机服务器说明.md](../联机服务器说明.md)。

## 1. 联机形态总览

| 形态 | 传输 | 人数 | 世界持久化 | 适用 |
| --- | --- | --- | --- | --- |
| **Python 服务器**（推荐） | WebSocket（`/ws`） | 每房间 ≤8 | 服务器 `server_data/{room}.json` | 局域网/公网多人共建 |
| **WebRTC 点对点**（备用） | DataChannel | 2 | 无（主机 localStorage） | 无法部署服务器时的双机联机 |

两种形态在客户端共用同一套消息处理（`handleNetworkMessage`），
通过 `netMode`（`'server'` / `'p2p'`）区分少量行为差异（如服务器专属的 `welcome/roomInfo`）。

## 2. 服务器架构（`server.py`，单文件 aiohttp）

### 2.1 路由

| 路由 | 处理 | 说明 |
| --- | --- | --- |
| `GET /`、`/index.html` | `web.FileResponse` | 静态首页 |
| `GET /assets/*` | `add_static` | 静态资源（`show_index=False` 防目录列举） |
| `GET /api/rooms` | `rooms_api` | 活跃房间列表 JSON（id/人数/容量/方块数/是否有密码），`no-store` + `CORS *` |
| `GET /ws?room=&name=&password=` | `websocket_handler` | 房间 WebSocket 入口 |

### 2.2 核心对象

```python
Client:  ws, name(≤18), id(secrets.token_hex(4)), can_build, chunks(分片重组缓冲)
Room:    id, data_dir, clients[], host, world(dict), shared(dict),
         password_hash, guest_can_build, save_task, dirty 状态
```

房间对象**懒创建**（首个连接者触发），全程驻留内存，退出时 `on_cleanup` 统一 flush。

### 2.3 房间生命周期

```
玩家A 连接 room=home（不存在）→ 创建 Room → A 成为 host → 请求 A 的世界快照
玩家B 连接同一房间         → 房间已有 world → 直接下发 snapshot
B 离开                    → 广播离开消息
A（主机）离开              → host 移交给 clients[0]，新 host 立即获得建造权
最后一个玩家离开           → Room 留存（省去重建），脏数据由 flush 落盘
```

### 2.4 密码与准入

- 房间**首次创建**时若带密码，则以 SHA-256 十六进制摘要存入 `password_hash`；
- 之后加入必须提供匹配密码（错误 → 关闭码 4005）；
- 对「创建时未设密码」的活跃房间提交密码 → 拒绝（4006），避免误解锁；
- 房间名规则：`^[A-Za-z0-9_-]{1,32}$`（不合法 → 4002）；
- 房间满员（8 人）→ 欢迎后立即关闭（4001）。

### 2.5 WebSocket 关闭码

| 码 | 含义 |
| --- | --- |
| 4001 | 房间已满 |
| 4002 | 房间名不合法 |
| 4003 | 消息超过 32 MB |
| 4004 | 被主机移出 |
| 4005 | 房间密码错误 |
| 4006 | 房间未设密码却收到密码 |

## 3. 消息协议

全部为 JSON 文本（`safe_json` 紧凑序列化，`ensure_ascii=false`）。
字段 `kind` 分派；通用机制：

- **分片**：任一端消息超过阈值即拆为 `kind:'_chunk'`（客户端 10 KB 阈值 / 9 KB 分片；
  服务器侧重组后递归处理）。32 MB 单帧上限双向一致。
- **方向记号**：C→S 客户端发服务器；S→C 服务器发客户端；S↔B 服务器广播（排除发送者）。

| kind | 方向 | 主要字段 | 服务端处理要点 |
| --- | --- | --- | --- |
| `_chunk` | C→S | id, i, total, data | 重组计数，齐了递归 `process`；解析失败回 error |
| `hello` | C→S / S↔B | name | 改名（≤18）广播 |
| `welcome` | S→C | role, room, clients, canBuild, selfId | 入房身份下发 |
| `roomInfo` | S↔B | clients, host, players[{id,name,canBuild,role}] | 成员变化全量名单 |
| `snapshot` | C→S（仅 host）/ S↔B | world[[key,val]…≤300k], shared… | 覆盖 world+shared；版本 <13 触发服务端迁移 |
| `requestSnapshot` | S→C（host） | — | 房间空时向主机索要世界 |
| `blocks` | C→S→B | items[{x,y,z,t}] ≤512 | 校验 `0≤x,z<128, −11≤y≤128, 0≤t≤64`；越界整条丢弃 |
| `block` | C→S→B | x,y,z,t | 同上单点版 |
| `shared` | C→S→B | 任意共享字段 | guest 发送时剥离 `worldTime/dayCount/raining/weatherTimer/adventureMode` |
| `environment` | C→S→B（仅 host） | worldTime, dayCount, raining, weatherTimer, adventureMode, cat, trackTrain, extraTrains | 主机权威环境（1Hz） |
| `chat` | C→S→B | text ≤120 | 原文广播 |
| `player` | C→S→B | x,y,z,yaw,pitch,style,selected,flying,mining,ridingTrain | 数值清洗后附加 clientId 广播 |
| `ping` / `pong` | C↔S | id | 延迟测量（3s 周期） |
| `checksum` | C(host)→S→B | hash | guest 比对本地世界哈希，不一致发 `syncRequest` |
| `syncRequest` | C→S | — | 服务器回 `snapshot`（房间当前权威世界） |
| `permission` | C(host)→S | canBuild, clientId? | 全局或定向开关 guest 建造权，落档 |
| `kick` | C(host)→S | clientId? | 踢出（可全踢） |
| `catRide` / `catCommand` | C→S→B | ridingTrain / mode,stayX,stayZ | 猫状态写 shared 并转发 |
| `error` | S→C | message | 校验失败提示 |
| `serverSaved` | S↔B | at | 服务器落档回执（客户端显示时间） |
| `kicked` | S→C | message | 被移出提示 |

## 4. 权限与安全模型

### 4.1 主机权威（Host Authority）

- **世界写入**：任何 `block/blocks/snapshot` 只有 host 或「被允许建造的 guest」可下发；
  服务器对无权者直接回 `permission` 拒绝。
- **环境状态**（时间/天气/冒险模式/猫/列车）：仅 host 的 `environment` 消息生效；
  guest 的 `shared` 中环境字段被服务器剥离。列车物理在各端本地模拟，host 以 1Hz
  广播权威状态校正（`applyTrackTrainState`）。
- **世界基准**：主机世界为初始基准；主机可导入备份 JSON/gz 覆盖联机地图并广播快照。
- **主机迁移**：host 掉线后首位幸存者自动接任，立即获得建造权并收到新 `welcome`。

### 4.2 服务器端防线（对恶意/异常客户端）

| 防线 | 实现 |
| --- | --- |
| 输入形状校验 | 每类消息字段类型/范围逐一清洗（坐标、枚举、长度截断） |
| 体素范围 | `0≤x,z<128`、`−11≤y≤128`、`0≤block≤64`，越界拒绝 |
| 体量上限 | 单消息 32 MB；snapshot ≤300,000 方块；blocks ≤512 条/帧 |
| 分片滥用 | chunk id ≤80 字符、total ≤1000、序号合法、重复分片幂等 |
| 名称/文本 | 昵称 ≤18、聊天 ≤120、房间名白名单正则 |
| 密码 | SHA-256 摘要存储，明文不落盘 |
| 静态目录 | `show_index=False`、`follow_symlinks=False` |
| 落档原子性 | 写 `.tmp` 后 `replace()`，避免半写文件 |

### 4.3 客户端闸门

`canNetworkEdit()`：未联机 / 是主机 / guest 且 `netCanBuild` 为真才允许建造类操作，
被拒时给出「主机暂时关闭了建造权限」提示；收到 `permission` 关闭时自动取消模板预览
并退出装修面板。

## 5. 客户端网络层

### 5.1 发送路径（`netSend`）

```
对象 → JSON 字符串
  ├─ ≤10KB → 直接 send
  └─ >10KB → 拆 9KB 分片（_chunk，自增消息 id）→ 对端重组
```

### 5.2 方块同步合并（`queueNetBlock`）

本地 `set()` 在联机且非应用远端数据时入队 `netPendingBlocks`：
满 128 条或 55ms 定时冲刷为一条 `blocks`——**高频挖掘/铺轨不会打满信道**。
`netApplying/netSuppress` 两个标志防止「应用远端数据 → 触发本地 set → 再广播」的回环。

### 5.3 定时器与节奏

| 定时器 | 周期 | 内容 |
| --- | --- | --- |
| 位置上报 | 100ms | `player`（含外观/选型/状态位） |
| 环境 | 1000ms | host：时间/天气/猫/列车 |
| ping + checksum | 3000ms | 延迟测量；host 附世界哈希 |
| 自动保存 | 60s | localStorage 冲刷 |
| pagehide | 即时 | 冲刷方块队列与存档 |

### 5.4 重连

- 开关式自动重连（默认开）：指数退避 `1s×2^n`，上限 10s；
- 密码错误/房间满/非法房间名自动停用重连（避免无意义循环）；
- 服务器配置（地址/房间）记忆在 `localStorage['minicraft-server']`。

### 5.5 远端玩家呈现

- 位置/朝向 10Hz 上报，本地 12/s 指数插值平滑；
- 每个远端玩家有**确定性 ID 哈希颜色**（名牌、目标框、地图点、小地图点）；
  模型复用本地玩家的盒件人形（含皮肤/服装/持物/挖掘挥臂/飞行姿态）；
- 5 秒无心跳的远端玩家隐藏；名牌经 MVP 投影定位到 DOM 层（45 格内）。

### 5.6 一致性自愈

host 每 3s 广播世界哈希（`worldHash`：FNV 变体，含方块数与键值混合）；
guest 比对失败即请求 `snapshot` 全量重同步——**最终一致**的兜底路径。
用户也可手动「发送完整世界同步」。

## 6. 同步策略总览

| 数据 | 传播方式 |
| --- | --- |
| 体素增删 | 增量 `block/blocks`（操作即同步，服务器校验后广播） |
| 门/灯/装修/轨道/列车等结构化状态 | `shared` 全量字段（本地变更后 180ms 防抖广播） |
| 时间/天气/猫/列车动态 | host `environment` 1Hz 权威广播 |
| 玩家位姿 | `player` 10Hz + 插值 |
| 全量世界 | `snapshot`（入房、导入地图、校验和修复、手动） |
| 聊天/猫命令 | 即时事件消息 |

## 7. WebRTC 备用通道

- 信令靠**人工复制粘贴**：主机「创建邀请」生成 offer SDP，加入者粘贴后「生成应答」，
  再把 answer 发回主机「应用应答」。流程在联机面板中分步引导。
- SDP 压缩：`CompressionStream('gzip')` + base64，前缀 `G:`；不支持压缩的浏览器回退
  base64 明文（前缀 `J:`）——连接码体积通常缩小一个数量级。
- ICE：单一 STUN 服务器（`stun:stun.l.google.com:19302`），收集超时 7s；
  DataChannel `ordered:true`，消息处理与服务器模式完全共用。
- 主机侧连接建立后 180ms 自动发送世界快照；权限/踢人等服务器型消息在此模式下
  由 host 客户端直接发送（P2P 星型拓扑中 host 即「服务器」）。

## 8. 服务器持久化

- **触发**：任何世界/shared 变更调用 `schedule_save()` 启动保存协程；
  每 0.5s 检查，满足「60s 无新变更」或「脏超过 60s」即落盘——高频建造只产生
  节流后的少量磁盘写入。落盘后广播 `serverSaved` 回执。
- **格式**：`server_data/{room}.json`：
  `{world: {"x,y,z": id}, shared: {...}, password_hash, guest_can_build, updated}`，
  临时文件 + 原子替换。
- **加载迁移**：启动加载时若 `worldVersion < 13`，用与客户端一致的
  `_migrate_legacy_world()`（Python 复刻版）把旧 64×64 世界升级为 128×128 深层世界，
  并立即落盘——**双端迁移算法保持位级一致**是该设计的硬约束（回归测试覆盖）。
- 应用退出（`on_cleanup`）时对所有房间 flush。

## 9. 典型时序

### 9.1 加入已有房间

```
B: GET /ws?room=home&name=旅人B
S: welcome{role:guest, canBuild, selfId}
S → 其他人: hello{name:旅人B}
S → B: snapshot{world, shared}          # 房间已有世界
S ↔ 全员: roomInfo{players[...]}
B: 每100ms player{...}   ↔  其他人渲染 B
```

### 9.2 guest 放置一个方块

```
B 本地 set() → queueNetBlock → (55ms/128条) → C→S blocks{items:[..]}
S 校验坐标/类型 → 写 Room.world → schedule_save → S↔其他人 blocks
其他人 netApplying 应用 → 45ms 防抖后 rebuildMesh + 小地图
```

### 9.3 世界漂移自愈

```
host: 每3s checksum{hash}
guest: 本地 worldHash() ≠ msg.hash → syncRequest
S → guest: snapshot{...}                # 服务器权威世界
guest: 清空世界 → 重建 → 存档 → 「完整世界同步完成」
```
