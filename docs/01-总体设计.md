# 01 · 总体设计

> 本文回答：项目是什么、为谁设计、整体如何分层、为什么这样选型、如何运行部署。

## 1. 项目概述

### 1.1 一句话定位

**MINICRAFT · 林间小屋** 是一个完全零依赖、浏览器直接打开即可游玩的 3D 体素沙盒游戏：
玩家在一片 128×128、带 10 层地下矿洞的方块森林中，回到奶奶留下的林间小屋，
围绕「归家」的叙事展开探索；同时可以在世界中自由建造，并铺设**木质铁路**——
从单条环线到带自动闭塞信号、车站巡线、感应分流与调车场的完整铁路网。

### 1.2 核心体验循环

```
        探索（地标 / 星晶 / 矿洞 / 营地 / 冰屋）
          │ 发现新区域，解锁故事与导航点
          ▼
        归家（小屋 / 壁炉 / 信箱 / 小猫 / 睡觉）
          │ 获得材料、生命恢复、每日信件与礼物
          ▼
        建造（方块 / 家具装修 / 铁路网）
          │ 消耗材料，表达创意，牵引更多探索
          ▼
        运营（列车巡线 / 调度 / 联机共建）
          │ 铁路把世界连成整体，朋友共建放大乐趣
          └──────────────► 回到「探索」
```

### 1.3 特性清单（现状）

- **世界**：128×128×(−11..128) 体素世界；草地、河流、湖泊、雪原、沙漠、绿洲、矿洞、
  营地、冰屋等地标；昼夜循环（约 6 分钟一天）、随机雨雪天气、星空与流星。
- **建造**：30+ 种方块的挖掘与放置、连续铺轨、建造撤销（40 步）、储物箱、方块工坊（6 种配方）。
- **铁路**：20 种轨道积木、自动吸附、线路自动识别、最多 4 列列车同图运行、
  自动闭塞信号、车站自动停靠与自动巡线（BFS 寻路 + 自动拨道岔/转盘）、
  感应轨联动、13 套内置模板 + 8 份自定义蓝图、轨道编辑撤销/重做。
- **生活玩法**：钓鱼与鱼群繁殖、菜园、伙伴猫「橘子」（亲密度/礼物/乘车的客车厢）、装修模式
  （16 种家具 × 2 层 × 主题/预设/多选/撤销重做）。
- **叙事**：9 章故事 + 7 封每日信件 + 15 项成就 + 主线任务链。
- **联机**：Python 房间服务器（推荐，≤8 人，房间密码、建造权限、聊天、主机权威世界）；
  WebRTC 手动点对点备用。
- **跨端**：桌面键鼠（Pointer Lock）与移动触屏（虚拟按键、滑动视角、双指缩放）双输入；
  三档画质自适应。

## 2. 设计目标与约束

### 2.1 目标

| # | 目标 | 落实方式 |
| --- | --- | --- |
| G1 | **零依赖、可离线分发** | 无 CDN、无框架、无构建；`index.html` + `assets/` + 可选 `server.py` 即为全部产物 |
| G2 | **单机可玩、联机可选** | `file://` 直开即完整可玩；服务器只是增强（多人 + 云端持久化） |
| G3 | **低配与触屏友好** | WebGL 1.0、分块网格、三档画质、触屏 UI、无纹理贴图（顶点色） |
| G4 | **存档可携带** | localStorage 自动保存；一键导出 gzip 备份，跨设备导入；联机主机可导入地图 |
| G5 | **铁路系统「安全拟真」** | 信号闭塞、行人避让、净空检测、车距控制——玩具外观、真实逻辑 |
| G6 | **多人协作安全** | 服务端坐标/类型校验、房间密码、主机权限开关、消息分片与大小上限 |

### 2.2 硬性约束（由 `tests/project_server_regression.py` 守护）

- `index.html` 必须小于 50 KB，且**不得包含内联 `<style>` / `<script>`**——
  逻辑全部在 `assets/minicraft.js`，样式全部在 `assets/minicraft.css`。
- `minicraft.js` 必须是**单个 IIFE**（`(() => { ... })();`），CSS 中不得出现 `http://` / `https://` 外链。
- `index.html` 引用的资源版本号（`?v=N`）必须与 JS 内的 `trackFeatureVersion` 一致
  （当前均为 41），保证发版时缓存一并失效。
- `index.html` 中 `getElementById` 引用的 DOM id 必须全部存在（≥200 个 id 被引用）。

### 2.3 明确的非目标（Non-Goals）

- 不做账号系统 / 中心化大厅 / 反作弊对抗（局域网与好友间游玩为假设场景）。
- 不做无限世界 / 区块流式加载（世界固定 128×128，换取简单与确定性行为）。
- 不做贴图与骨骼动画（顶点色 + 盒件组装是刻意的美术选择）。
- 不做服务器端游戏逻辑模拟（服务器只做转发、校验与持久化，权威在主机客户端）。

## 3. 总体架构

### 3.1 部署视图

```
┌─────────────────────────────── 浏览器 ────────────────────────────────┐
│  index.html        页面骨架：canvas 分层、HUD、全部面板 DOM            │
│  minicraft.css     界面样式、层叠顺序、响应式与触屏适配                │
│  minicraft.js      WebGL 游戏运行时（单文件 IIFE，约 1500 行）          │
│    ├─ 渲染管线     WebGL 1.0 + 单着色器程序 + 分块静态网格 + 动态实体   │
│    ├─ 世界数据     稀疏 Map<"x,y,z", blockId> + 版本迁移               │
│    ├─ 玩家/物理    AABB 碰撞、轨道面站立、飞行、相机（3 视角）          │
│    ├─ 玩法系统     任务/成就/故事/制作/钓鱼/菜园/猫/装修/生存           │
│    ├─ 轨道列车     轨道图结构、列车模拟、信号、寻路、模板（见 04）      │
│    ├─ 网络层       WebSocket 客户端（推荐）或 WebRTC DataChannel（备用）│
│    └─ 存档         localStorage + gzip 备份导入导出（见 06）            │
└───────────────┬────────────────────────────────┬─────────────────────┘
                │ WebSocket（JSON，大消息自动分片） │ WebRTC DataChannel
┌───────────────▼────────────────────────┐   ┌───▼─────────────────────┐
│ server.py（aiohttp，单文件）            │   │ STUN: stun.l.google.com  │
│  ├─ GET /            静态首页           │   │ （offer/answer 手工交换，│
│  ├─ GET /assets/*    静态资源           │   │   连接码 gzip+base64）   │
│  ├─ GET /api/rooms   活跃房间列表       │   └─────────────────────────┘
│  └─ GET /ws?room=&name=&password=       │
│     └─ Room：≤8 客户端、主机制、校验、    │
```

### 3.2 客户端逻辑分层（`minicraft.js` 内部顺序）

| 层 | 代表函数 / 数据 | 职责 |
| --- | --- | --- |
| 着色器管线 | `vs` / `fs` / `shader()` | 编译唯一一个着色器程序：雾、8 盏点光源、水面波动/菲涅尔、灯闪烁 |
| 世界数据 | `world: Map`、`get/set`、`buildWorld()` | 稀疏体素存储；`set()` 在联机时自动入队网络同步 |
| 世界生成 | `buildLargeHouse/buildCave/buildExpansion/buildFarlands/buildOuterWorldFeatures` | 确定性程序化生成 + 存档版本迁移复用 |
| 网格构建 | `rebuildMesh()`、`pushBox/pushWindow/pushTrackPiece…` | 遍历世界生成分块静态网格与各专用缓冲 |
| 轨道系统 | `trackPieces[]`、`trackPorts/trackCells/…`（见 04） | 轨道积木、图结构、列车模拟、寻路、模板 |
| 玩家与物理 | `update()`、`collides()`、`raycast()` | 移动、重力、碰撞、视线检测、区域事件 |
| 交互 | `interact()`、`beginMining/beginPlacing` | 统一 E 键交互分派、挖掘/放置 |
| 玩法系统 | `useChest/updateCat/updateFishing/…` | 各生活与叙事子系统 |
| 联机 | `netSend/handleNetworkMessage/…` | 消息收发、分片重组、远端玩家插值 |
| 存档 | `buildSaveJson/loadGame/flushSave` | 序列化、迁移、自动保存 |
| 渲染循环 | `loop()/render()` | rAF 主循环：`update(dt)` → 各子系统 → `render()` → `drawWeather()` |
| UI/输入 | `updateHud/drawMinimap`、事件监听块 | HUD 刷新、面板管理、键鼠/触屏输入 |

### 3.3 主循环时序

```
requestAnimationFrame(loop)  — 目标 60 FPS，dt 上限 0.045s（防卡顿穿墙）
  ├─ update(dt)               started && !paused 才推进
  │   ├─ 时间/天气推进（guest 端时间由主机 environment 消息驱动）
  │   ├─ 玩家移动（WASD/飞行/轨道乘坐）
  │   ├─ 重力与碰撞（含轨道面站立 trackLandingHeight）
  │   ├─ updateSlimes / updateTrackTrain / updateExtraTrains / updateCat
  │   ├─ updateCrossingGates / updateDrawbridges（道口栏杆、升降桥动画）
  │   ├─ updateFishing / updateGarden / updateMining / updatePlacing
  │   └─ 区域触发（进屋/发现矿洞/营地/冰屋 → 成就与故事）
  ├─ updateRemotePlayers(dt)  远端玩家位置插值（始终运行）
  ├─ render()                 分块网格 + 全部动态实体绘制（见 02）
  └─ drawWeather(dt)          雨/雪粒子（2D canvas 叠加）
每 1s（节流）：updateHud 内部每 4 帧重绘小地图；每 600ms 更新 FPS 统计
定时器：player 位置 10Hz 上报；environment 1Hz（仅主机）；ping/checksum 3s；自动保存 60s
```

## 4. 技术选型与理由

| 领域 | 选型 | 理由与权衡 |
| --- | --- | --- |
| 渲染 | 裸 WebGL 1.0 | 相比 three.js：体积为零、完全可控、兼容最广（ mediump 着色器即可）；代价是手写矩阵/网格工具（`perspective/lookAt/pushBox`），但体素渲染恰好只需盒子与线 |
| 美术 | 顶点色 + 程序化配色 | 无贴图 = 无加载、无跨域、无内存压力；`blockColor()` 按面/坐标做条纹、砖纹、脉冲等程序化变化 |
| 客户端语言 | ES2020 级 vanilla JS，单 IIFE | 满足「无构建」约束；单文件便于整体加载与语法检查（`node --check`） |
| 服务端 | Python + aiohttp | 单文件提供 HTTP 静态托管与 WebSocket；`asyncio` 天然适配房间广播；部署只需 `pip install aiohttp` |
| 传输格式 | JSON 文本 + 应用层分片（`_chunk`） | 调试友好；32 MB 消息上限 + 9KB 分片规避单帧过大；连接码用 `CompressionStream` gzip 压缩 |
| 存档 | localStorage + 可选 gzip 文件 | 免服务端；quota 溢出降级到内存存档并提示导出 |
| 音效 | WebAudio 振荡器合成（`tone()`） | 零音频资产；脚步/挖掘/鸣笛/UI 全部程序化音色 |
| 备用联机 | WebRTC DataChannel + 手工交换 SDP | 无需任何服务器即可双人联机；SDP  gzip+base64 后前缀 `G:`/`J:` 区分压缩与明文 |
| 确定性生成 | 整数哈希（`Math.imul`） | 地下矿层、外区地貌、树木分布由坐标哈希决定，客户端与服务器迁移逻辑可保持一致 |

## 6. 运行与部署

### 6.1 三种运行形态

| 形态 | 命令 | 联机 | 存档 |
| --- | --- | --- | --- |
| 纯本地 | 直接用浏览器打开 `index.html` | 无（或 WebRTC 备用） | localStorage（`file:` 协议下仍可用） |
| Python 服务器 | `python3 server.py --host 0.0.0.0 --port 8765` | 推荐：默认连 `home` 房间 | localStorage + 服务器 `server_data/home.json` 双份 |
| 一键脚本 | `./start_server.sh` / `启动服务器.bat` | 同上 | 同上 |

### 6.2 服务器参数

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--host` | `0.0.0.0` | 监听地址 |
| `--port` | `8765` | HTTP 与 WebSocket 共用端口 |
| `--data-dir` | `server_data` | 房间存档目录（相对仓库根解析） |

### 6.3 客户端自动连接行为

页面通过 HTTP（非 `file:`）打开时，加载 800ms 后自动连接默认服务器地址（同源 `/ws`）的
`home` 房间；URL 参数可覆盖：`?room=xxx`（房间名）、`?server=ws://...`（服务器地址）、
`?autoconnect=0`（禁用自动连接）。联机面板中可复制带这些参数的房间链接给其他玩家。

## 8. 设计权衡与已知限制

### 8.1 主要权衡记录

1. **主机权威 vs 服务器权威**：列车物理、时间、猫等环境状态由**主机客户端**模拟并周期广播，
   服务器只校验与转发。取舍：服务器保持极简（无游戏逻辑），代价是主机掉线瞬间环境状态
   依赖快照恢复、guest 端 1 秒内的本地模拟会被主机状态覆盖校正。
2. **稀疏 Map vs 三维数组**：世界用 `Map<"x,y,z", id>` 存储，空气不占内存；
   代价是网格重建需遍历全表（约 20 万方块，实测可接受，且只在改动时触发）。
3. **静态分块网格 + 动态实体缓冲**：世界几何按 16×16 分块重建、按距离剔除绘制；
   列车/生物/家具每帧重建进单个动态缓冲。取舍：避免场景图与 VAO 抽象，简单直接。
4. **JSON 文本协议**：可读可调试；大消息走应用层分片而非切到二进制，保持实现简单。
5. **固定 128×128 世界**：所有索引（轨道列索引、小地图、服务器校验）都可假定边界，
   大幅简化正确性推理。

### 8.2 已知限制与演进方向

- 单存档槽位（一个 localStorage 键）；如需多档可用备份文件手动切换。
- 网格重建为全量重建，超大规模改动时可能有单帧尖峰；可演进为脏块局部重建。
- 无贴图与光照烘焙；夜间仅 8 盏最近点光源 + 全局环境光近似。
- 服务器无鉴权，房间名即命名空间；公网部署建议自行加反向代理与 TLS。
- 远端玩家位置为 10Hz 上报 + 本地插值，快速移动时会有轻微平滑延迟（设计上可接受）。
